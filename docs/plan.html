00

Scope guard

Read this section on the morning you feel the urge to add something. Three weeks is roughly fifteen working days after life takes its cut. A feature added in week two is a feature that steals from the benchmark in week three.

In scope — build exactly this

  • Paste create, read, delete — anonymous and authenticated
  • JWT auth with refresh-token rotation
  • Stack-trace parsing for two runtimes: Node and Python
  • Fingerprint grouping of identical errors across users
  • Trending pastes, computed from a Redis sorted set
  • Redis read cache, buffered view counters, rate limiting
  • A load test with honest before/after numbers
  • Deployed at a URL a stranger can open

Out of scope — do not build these

  • Kafka, microservices, Kubernetes, a service mesh
  • Teams, orgs, roles, anything past owner-vs-anonymous
  • Fifty-language syntax highlighting — five is plenty
  • Custom domains, paid tiers, billing
  • Comments, reactions, follows, notifications
  • A mobile app
  • A third stack-trace runtime
  • Rewriting the codebase in another language mid-project
The rule that decides every argument

If you cannot state the bottleneck a dependency solves in one sentence containing a number, remove the dependency. If you finish early, spend the time on DSA, not features.

02

Architecture

One Express process. Do not split it. A monolith you can explain from memory beats microservices you narrate from a diagram. The only concurrency in the system is a single background interval that flushes view counters, and that one detail is the source of the most interesting scaling question in the whole project.

The two request paths that matter

PathSequenceTarget
Read a paste
GET /api/pastes/:slug		rate-limit check → GET paste:{slug} → hit: return, set X-Cache: HIT → miss: Mongo findOne({slug}) on the unique index, SETEX 1h → fire-and-forget INCR views:{slug} + SADD views:dirty + ZINCRBY trending:{hour}p99 < 50 ms cached
Create a paste
POST /api/pastes		rate-limit → Zod validate → size cap → detect kind → if stacktrace: parse, normalize, hash → insert paste → atomic upsert on fingerprints with $inc → return slugp99 < 250 ms
Decision that pays off in week three

Put the cache behind a single env flag, CACHE_ENABLED, from the first day you write the cache service. Your before/after benchmark then changes exactly one variable — same binary, same machine, same dataset, one boolean — instead of comparing two git branches and hoping nothing else moved. This is the difference between a number an interviewer believes and a number they poke holes in.

Why app.js and index.js are separate

users & fingerprints

users — email unique, passwordHash (bcrypt cost 12), createdAt, tokenVersion. Bumping tokenVersion invalidates every outstanding refresh token for that user in one write, which is your answer to "JWTs can't be revoked."

fingerprints — one document per unique error signature, with _id set to the hash itself so the upsert needs no secondary lookup. Fields: errorType, normalizedMessage, topFrame, runtime, count, firstSeenAt, lastSeenAt.

Sparse vs partial — know the difference

Most pastes are plain code and have no fingerprint, so indexing all of them wastes space and cache residency. A sparse index skips documents where the field is absent. A partial index takes an arbitrary filter expression — { fingerprint: { $exists: true } } — and is the modern, strictly more flexible option. Use partial, and be able to explain that sparse is the older special case of it. Then quote the size difference: run db.pastes.stats().indexSizes with and without, and put the number in your README.

Index hygiene

Declare indexes in the Mongoose schema, but do not rely on autoIndex in production — it builds on every boot. Set autoIndex: false and run a one-line syncIndexes() script as an explicit migration step. Verify each query with .explain("executionStats") and check for IXSCAN, not COLLSCAN, and for totalKeysExamined close to nReturned. Screenshot one explain output for the README.

Auth design, concretely

TokenLifetimeStoredWhy
Access15 minIn memory on the client, sent as Authorization: BearerShort enough that revocation lag is tolerable; in memory rather than localStorage so an XSS cannot read it off disk
Refresh7 dayshttpOnly; Secure; SameSite=Lax; Path=/api/auth/refreshJavaScript cannot touch it, and the narrow path means it is not sent on every request

Rotate the refresh token on every use. Carry tokenVersion in the refresh payload and compare it against the user document — that gives you instant global logout with one field and no denylist. The client wrapper must queue concurrent 401s and refresh exactly once, otherwise three parallel requests trigger three rotations and two of them lose the race.

The bcrypt detail worth knowing

Cost 12 is roughly 250 ms of deliberate CPU. Use the async API — it runs on libuv's threadpool, which defaults to four threads. That means five simultaneous logins queue, and a burst of thirty will visibly stall unrelated requests. Measure it once with autocannon against /api/auth/login, write the number down, and you have a genuinely sophisticated answer ready for "what happens under load?"

The fingerprint engine

This is the part that makes the project not a clone of something else. Get it right and it carries the entire interview. Budget seven days for it and protect them.

The problem: two people hit the same bug. Their traces differ in line numbers, absolute paths, timestamps, object ids, container hostnames and which library versions sit in the frames. A naive hash of the text groups nothing at all — every trace is unique, and the feature is worthless.

Step 1 — detect the runtime

Score the input against both shapes and take the winner, rather than committing on the first match. Ambiguous input returns null and the paste is stored as a plain log — failing to parse is a perfectly good outcome and must never throw.

Node     at fnName (/srv/app/handlers/user.js:42:15)
         at async Server.<anonymous> (node:internal/http:1420:9)

Python   Traceback (most recent call last):
           File "/srv/app/handlers/user.py", line 42, in get_user
             return cache[user_id]

Step 2 — parse into structured frames

Each frame becomes { file, line, col, function, isApp }. The cases that will bite you, and that you should have a fixture for each of: at async, at new ClassName, at Object.<anonymous>, frames with no function name, file:// URLs, node:internal/* paths, Windows drive letters, and — on the Python side — chained exceptions. When Python prints "During handling of the above exception, another exception occurred", there are two tracebacks in the text and you want the last one, because that is the error that actually escaped.

Step 3 — normalize the message

Strip everything that varies between two occurrences of the same bug. Rule order matters — run the specific patterns before the general ones, or the bare-number rule will shred your UUIDs and timestamps before they are recognised.

Step 4 — keep only application frames

This is the key insight, and it is the sentence to say out loud in an interview: library frames differ between users; application frames identify the bug. A TypeError thrown from somewhere inside Express tells you nothing — half the internet has that frame. The first frame in your code tells you everything.

RuntimeDiscard a frame when its path…
Nodecontains node_modules/, starts with node: or internal/, is <anonymous>, or is a bundler runtime chunk
Pythoncontains site-packages/ or dist-packages/, matches a stdlib path like lib/python3.*/, or is <frozen importlib._bootstrap>
The edge case you will be asked about

What if every frame is vendor code — a crash entirely inside a library, with no application frame at all? Filtering leaves you nothing to hash. Fall back to the top three frames overall, and set a flag on the parsed object recording that you did. Having thought about this before being asked is worth more than the fix itself.

Step 5 — hash

fingerprint = sha1(
    errorType + "|" +
    normalizedMessage + "|" +
    topAppFrames.slice(0, 3)
      .map(f => basename(f.file) + ":" + f.function)
      .join("|")
  ).slice(0, 16)

Note what is deliberately absent from that input. No line numbers: adding an import at the top of a file shifts every line below it, and the same bug must still group after an unrelated edit. No absolute paths, only basenames: /home/ani/app/user.js and /srv/prod/app/user.js are the same file. No column numbers, no timestamps, no versions.

Sixteen hex characters is 64 bits. By the birthday bound you expect your first collision somewhere around four billion distinct error signatures, which is several orders of magnitude past anything this system will ever hold. Say that number rather than "it's probably fine."

The write must be atomic

await Fingerprint.updateOne(
  { _id: fp },
  {
    $inc:        { count: 1 },
    $max:        { lastSeenAt: now },
    $setOnInsert: { errorType, normalizedMessage, topFrame, runtime, firstSeenAt: now }
  },
  { upsert: true }
);

One round trip, no read-modify-write, no lost updates under concurrency. Two simultaneous upserts of a brand-new fingerprint can still race and produce a duplicate-key error on _id — catch code 11000 and retry once, at which point the document exists and the $inc path applies.

The test suite that sells the project

Collect twenty real stack traces — pull them from your own projects, from GitHub issues, from Stack Overflow. Save each as a fixture file alongside a label saying which group it belongs to. Then do not test them one at a time: test every pair.

// 20 traces -> C(20,2) = 190 pairs
// For each pair, assert: same group label  ⟺  same fingerprint

              predicted same    predicted different
actual same        TP                  FN   (missed a grouping)
actual different   FP                  TN   (grouped two real bugs — worse)

Report precision and recall over those 190 pairs, not a single accuracy percentage — and note in the README that false positives are the expensive error, because merging two genuinely different bugs hides one of them forever, while a missed grouping merely shows a duplicate. That framing is what separates a student answer from an engineer's.

Known limitation — state it before they find it

Because line numbers are excluded, two different errors thrown from the same function with the same message shape will collide into one group. That is a deliberate trade: it is the price of surviving ordinary code edits, and the alternative — including line numbers — breaks grouping on every commit. Leading with this trade-off is one of the strongest moments available to you in the interview.

Redis keyspace

Do not add Redis until week three, and only after you have measured life without it. The entire point is the before and after. When you do add it, design the keyspace on paper first.

KeyTypeTTLWritten byRead by

Why the dirty set exists

Without it, the flush job has to find which counters changed, and the only way to do that is to scan the keyspace. KEYS views:* is O(N) over every key in the database and blocks the single-threaded server while it runs — it is a production outage waiting for a quiet Tuesday. SCAN is safer but still walks everything. A dirty set makes the flush proportional to what actually changed. Never call KEYS. Be able to say why.

The flush job, and the bug everyone writes first

The naive version reads the counter, writes it to Mongo, then deletes the key — and silently loses every view that arrived in between. The correct shape:

const slugs = await redis.spop('views:dirty', 500);        // claim a batch
const deltas = await Promise.all(
  slugs.map(s => redis.getset(`views:${s}`, 0))             // atomic read-and-reset
);

try {
  await Paste.bulkWrite(slugs.map((s, i) => ({
    updateOne: { filter: { slug: s }, update: { $inc: { views: Number(deltas[i]) } } }
  })), { ordered: false });
} catch (err) {
  // put the deltas back, or you have silently thrown away view counts
  await Promise.all(slugs.map((s, i) => redis.incrby(`views:${s}`, Number(deltas[i]))));
  await redis.sadd('views:dirty', ...slugs);
  throw err;
}

Increments arriving between the GETSET and the Mongo write are not lost — they accumulate on the freshly zeroed key and get picked up next cycle. The only real hazard is the Mongo write failing after you have already zeroed, which is exactly what the catch block repairs.

One more detail: the number you display is mongo.views + redis.views:{slug}. Show only the Mongo value and the count visibly jumps backwards right after each flush, which looks broken to anyone watching.

Rate limiting — sliding window in Lua

The check and the increment must be one atomic operation, or two concurrent requests both read "9 of 10" and both proceed. A Lua script runs atomically inside Redis, which is the whole reason it is here.

-- KEYS[1] window key   ARGV: now_ms, window_ms, limit, unique_id
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])
local used = redis.call('ZCARD', KEYS[1])
if used >= tonumber(ARGV[3]) then
  return { 0, used }
end
redis.call('ZADD',   KEYS[1], ARGV[1], ARGV[1] .. '-' .. ARGV[4])
redis.call('PEXPIRE', KEYS[1], ARGV[2])
return { 1, used + 1 }
The trade-off to raise before they do

A sliding-window log stores one sorted-set member per request in the window — precise, but at 300 reads/min/IP that is 300 members held per active IP, and memory scales with traffic. So use it only where precision matters and volume is low: the create endpoints. For the 300/min read limit, use a fixed-window INCR plus EXPIRE — two commands, constant memory, and the only cost is a burst allowed at a window boundary, which for read traffic is irrelevant. Picking different algorithms for different endpoints, and knowing why, is a much better answer than using one everywhere.

Decide the failure posture now

Redis goes down. Does the limiter fail open or closed? Recommended: fail open on reads — a cache outage should not take the site down — and fail closed on anonymous creates, since that endpoint is the actual abuse target. Log loudly either way. Having a deliberate answer here reads as operational maturity; "I hadn't thought about it" does not.

The one-sentence justification for each Redis use

  • Cache: "Paste reads were N ms at p99 against Mongo; cached they are M ms, at a K% hit rate under a realistic skewed load."
  • Counters: "A Mongo write per page view does not scale; buffering in Redis cut write ops/sec from X to Y."
  • Trending: "Computing it in Mongo is an aggregation with a sort over a growing collection at Z ms; a sorted set is O(log N) to write and O(log N + M) to read."
  • Rate limit: "Anonymous creation is an open write endpoint; the check and increment must be atomic, which is why it's a Lua script."

Fill in every letter with a number you measured. That sentence, four times, is most of section twelve.

09

The benchmark

This becomes a line on your resume, so the methodology has to survive scrutiny. The rules below are what make the numbers honest — and an interviewer who knows load testing will check for exactly these.

#RuleWhy it matters
1Seed 5–10k pastes firstBenchmarking an empty database proves nothing — everything fits in RAM and Mongo looks infinitely fast.
2Use a skewed access distributionReal traffic is skewed; 80% of reads hitting 20% of pastes is roughly right. Uniform random access makes caching look worse than it is, and an interviewer will ask which you used.
3Change exactly one variableSame machine, same script, same dataset, same binary — only CACHE_ENABLED moves.
4Warm up, then measureDiscard the first 30 seconds. JIT, connection pools and the OS page cache all need to settle.
5Run locally, not on the free tierRender and Atlas free tiers are CPU-throttled and shared, so you would be measuring someone else's noise. Benchmark on your own machine; deploy for the demo.
6Commit the raw outputBoth k6 JSON summaries go in the repo. Numbers with evidence behind them read completely differently.
 
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  stages: [
    { duration: '30s', target: 50 },   // warm-up — discarded
    { duration: '2m',  target: 200 },
    { duration: '30s', target: 0 },
  ],
  thresholds: {
    http_req_duration: ['p(99)<500'],
    http_req_failed:   ['rate<0.01'],
  },
};

const SLUGS = JSON.parse(open('./slugs.json'));

// Zipfian-ish: 80% of traffic hits 20% of pastes
function pickSlug() {
  const hot  = Math.random() < 0.8;
  const pool = hot ? Math.floor(SLUGS.length * 0.2) : SLUGS.length;
  return SLUGS[Math.floor(Math.random() * pool)];
}

export default function () {
  const res = http.get(`${__ENV.BASE}/api/pastes/${pickSlug()}`);
  check(res, { 'status 200': (r) => r.status === 200 });
}

12

Interview defense

Write each of these out in your own words during phase 7, then say them aloud. The goal is not memorisation — it is having already had the thought once, so the answer arrives as recall rather than improvisation.

Why is the compound index { fingerprint: 1, createdAt: -1 } in that order?

Equality before sort. Mongo seeks directly to the fingerprint prefix, and entries inside that prefix are already stored in descending createdAt order, so results come back sorted out of the index with no in-memory sort stage. Reversed, the index can't seek to a fingerprint at all and the query degrades to a scan.

Why partial rather than a plain index on fingerprint?

Most pastes are ordinary code with no fingerprint at all. A partial index only stores documents matching a filter, so the index is smaller and more of it stays resident in memory. Sparse is the older special case of the same idea.

Why not just hash the whole stack trace?

The grouping rate would be approximately zero. Paths, line numbers, timestamps and object ids all differ between two occurrences of the same bug, so every trace hashes uniquely and the feature does nothing.

Why exclude line numbers from the hash?

So the same bug still groups after an unrelated edit shifts the file. The cost is that two different errors in the same function with the same message shape collide — a deliberate trade, and the one I would revisit first if false positives showed up in real data.

What's your collision probability?

Sixteen hex characters is 64 bits, so by the birthday bound the first expected collision is around four billion distinct signatures. That's several orders of magnitude beyond anything this system will hold.

Why Redis instead of another Mongo index?

Three different reasons, each with a number. Reads: the cache took p99 from X to Y at a Z% hit rate. Views: a Mongo write per page view doesn't scale, and buffering cut write ops/sec by N%. Trending: an aggregation with a sort over a growing collection versus O(log N) on a sorted set.

What happens when Redis goes down?

Reads fall through to Mongo — every cache call is wrapped so a Redis error logs and continues. Buffered view counts in flight are lost, which is acceptable for a view counter and stated as such. The rate limiter fails open on reads and closed on anonymous creates, because that endpoint is the actual abuse target. I tested this by killing the container mid-load-test.

How do you invalidate the cache?

Delete on write, with a one-hour TTL as a backstop. TTLs carry jitter so a batch of keys created together doesn't expire together and stampede Mongo. 404s are negatively cached for sixty seconds so slug scanning can't hammer the database.

Why is KEYS never in this codebase?

It's O(N) over the entire keyspace and blocks Redis's single thread while it runs. The dirty-set pattern makes the flush proportional to what actually changed instead.

Why bcrypt cost 12, and what does it cost you?

About 250 ms of deliberate CPU per hash. I use the async API, which runs on libuv's threadpool — four threads by default — so simultaneous logins queue and a burst stalls unrelated requests. I measured it; the number is in the README.

Where does this system actually break?

Under a ramp past 200 virtual users, [the component you found] saturates first. The single Node process is also one core, and the view flusher is a singleton — run two instances and both flush the same dirty set, so horizontal scaling needs either a leader election or moving the flush out to its own worker. That's the first thing I'd fix.

How would you take this to ten times the traffic?

Horizontal Node behind a load balancer first, since the API is stateless — with the flusher extracted to a single worker. Then a CDN in front of /raw, which is immutable content and trivially cacheable at the edge. Then Mongo secondary reads for the occurrence lists, which tolerate staleness. Fingerprinting moves to a queue so the create path returns before parsing finishes. I'd do them in that order because that's the order the measurements point at.

Definition of done

Three things must be true on day 21. Everything in this plan exists to make them true.

1 · A measured before and after

The table in section 09, filled in, with the test configuration printed next to it and both raw k6 outputs committed.

2 · A reason for every dependency

One sentence each, containing a number you measured yourself. Four of them are drafted at the end of section 07.

3 · A known failure mode

"It falls over around 2k concurrent because the Mongo connection pool saturates, and I'd fix it with X" beats "it handles everything fine" by a mile. Engineers know their system's limits; students claim there are none.
